Give your ADK travel agent a memory with Vertex AI Memory Bank

    Overview

    3 min

    In this codelab you connect a trip-planning agent built with the Agent Development Kit (ADK) to Vertex AI Memory Bank, so the agent remembers guests across sessions. For example, it remembers that a guest travels with a dog named Oreo.

    There are two ways to put memories into a Memory Bank:

    1. Write one fact directly

    CreateMemory / generate
    Fact

    Use when your app already knows something, for example from a booking form. No transcript needed.

    2. Archive a whole chat

    Path 1 is our own helper code in memory_bank/memories.py. Path 2 is built into ADK, and the agent in travel_agent/agent.py calls it at the end of every turn. To read memories back, the agent uses PreloadMemoryTool, which searches memory before the model answers.

    What you'll build

    • Memory topics that decide what the bank remembers, and a Memory Bank that uses them
    • A CLI that writes facts directly with memories.create, plus a memories.generate variant
    • Reads with list and retrieve
    • An ADK agent that archives whole sessions and recalls memories, backed by Memory Bank

    What you'll need

    • A Google Cloud project with billing enabled
    • Python 3.12+, Node.js (for the Airbnb MCP server via npx), and the gcloud CLI
    • A Gemini API key

    Memory topics and the Memory Bank

    10 min

    A Memory Bank lives inside an Agent Engine (reasoning engine). When you create it, you can tell it what to extract from conversations by defining memory topics.

    What is a memory topic?

    A memory topic tells Memory Bank what kind of information is worth remembering. When Memory Bank reads a conversation, a model extracts only the facts that fit a topic. Anything that fits no topic is dropped.

    KindWhat it is
    custom_memory_topicYour own topic: a label plus a description. This project uses these.
    managed_memory_topicBuilt-in topics from Google: USER_PERSONAL_INFO, USER_PREFERENCES, KEY_CONVERSATION_DETAILS, EXPLICIT_INSTRUCTIONS. Used by default when you set no topics.

    This project defines two custom topics for a hotel guest:

    LabelWhat it keepsExample
    stay_preferenceRoom, bed, smoking, pets, view, amenities, budgetGuest wants a non-smoking room and can bring a dog.
    trip_contextDestination, dates, who's traveling, purpose, dietary or accessibility needsGuest is traveling to Chiang Mai with a golden retriever named Max.
    memory_bank/memories.py
    def travel_memory_topics():
    types = vertexai.types
    MemoryTopic = types.MemoryBankCustomizationConfigMemoryTopic
    CustomMemoryTopic = types.MemoryBankCustomizationConfigMemoryTopicCustomMemoryTopic

    return [
        MemoryTopic(
            custom_memory_topic=CustomMemoryTopic(
                label="stay_preference",
                description="""Extract the guest's hotel and room preferences. Include:
                - Room type (single, double, suite, connecting rooms)
                - Smoking or non-smoking
                - Pets (bringing a pet, type, size)
                ...
                Example: "Guest wants a non-smoking room and can bring a dog."
                """,
            )
        ),
        MemoryTopic(
            custom_memory_topic=CustomMemoryTopic(
                label="trip_context",
                description="""Extract the guest's trip context. ...""",
            )
        ),
    ]
    Write the description like a prompt

    The description is the instruction the extraction model reads. List what to include and add one or two Example: lines in the style you want stored. Clearer descriptions give more consistent memories.

    When topics apply

    Write pathUses topics?
    add_session_to_memory (ADK, path 2)Yes, facts are extracted from the chat
    memories.generateYes
    memories.create (custom_add, path 1)No, the fact is stored as given

    For example, if a guest types “I'd like a non-smoking room, and I love really spicy food,” Memory Bank keeps “Guest wants a non-smoking room.” The spicy food fits neither topic, so it's dropped. To keep it, add a topic such as food_preference.

    Create the bank with the topics

    The topics go into the bank's config when it's created:

    memory_bank/memories.py
    def create_memory_bank(display_name="travel-agent-memory") -> str:
    client = get_client()   # vertexai.Client(project, location)
    engine = client.agent_engines.create(
        config={
            "display_name": display_name,
            "context_spec": {
                "memory_bank_config": {
                    "customization_configs": [
                        vertexai.types.MemoryBankCustomizationConfig(
                            memory_topics=travel_memory_topics(),
                        )
                    ],
                }
            },
        },
    )
    return engine.api_resource.name

    Run it

    python -m memory_bank create

    After a short wait you'll see something like:

    projects/123456/locations/us-central1/reasoningEngines/987654321
Set AGENT_ENGINE_ID to: 987654321

    Put the last number in AGENT_ENGINE_ID in .env. memory_bank_name() builds the full resource name for you. You can also paste the full projects/... name.

    Topics belong to the bank

    Topics are saved with the bank when it's created. Changing travel_memory_topics() later doesn't change a bank that already exists. Update that bank's config or create a new bank.

    Scope

    Every memory belongs to a scope. Here the scope is {"app_name": "travel_agent", "user_id": ...}, the same keys ADK uses when it searches. If any scope key doesn't match, the agent can't see the memory.

    Path 1: Write a fact directly

    10 min

    Use this when your app already knows something, for example the guest ticked “bringing a pet” on a booking form. The guest doesn't have to tell the agent.

    CreateMemory: store the text exactly

    memory_bank/memories.py
    def custom_add(fact: str, user_id: str, app_name: str = "travel_agent"):
    text = fact.strip()
    if not text:
        raise ValueError("fact must not be empty")

    client = get_client()
    return client.agent_engines.memories.create(
        name=memory_bank_name(),
        fact=text,
        scope={"app_name": app_name, "user_id": user_id},
        config={"wait_for_completion": True},
    )
    python -m memory_bank add --user-id user --fact "Guest is traveling with a dog named Oreo."

    The CLI prints the fact and the new memory's resource name. create doesn't merge with existing memories, so running it twice with the same text gives you two entries.

    generate: merge with what's already there

    To have a new fact consolidated with existing memories (for example, updating “one dog named Oreo” to “two dogs”), send it through generate with direct_memories_source. This function isn't in the repo yet. Add it as an exercise.

    memory_bank/memories.py (add this)
    def generate_fact(fact: str, user_id: str, app_name: str = "travel_agent"):
    """Send a fact through generation so it is merged with existing memories."""
    client = get_client()
    return client.agent_engines.memories.generate(
        name=memory_bank_name(),
        direct_memories_source={"direct_memories": [{"fact": fact.strip()}]},
        scope=_scope(user_id, app_name),
        config={"wait_for_completion": True},
    )

    Read memories back

    5 min

    list_memories picks the API based on whether you pass a user_id:

    memory_bank/memories.py
    def list_memories(user_id=None, app_name="travel_agent") -> list:
    client = get_client()
    name = memory_bank_name()
    if user_id:
        # RetrieveMemories: every scope key must match
        return list(client.agent_engines.memories.retrieve(
            name=name, scope=_scope(user_id, app_name),
        ))
    # ListMemories: every memory in the bank
    return list(client.agent_engines.memories.list(name=name))
    python -m memory_bank list --user-id user
python -m memory_bank list          # all users
    1. Guest is traveling with a dog named Oreo.
   projects/.../reasoningEngines/987654321/memories/1122334455

    Similarity search

    Add similarity_search_params to get only the memories closest to a query. ADK searches this way while the agent runs (step 6).

    client.agent_engines.memories.retrieve(
    name=memory_bank_name(),
    scope={"app_name": "travel_agent", "user_id": "user"},
    similarity_search_params={"search_query": "pets", "top_k": 3},
)

    memory_fact() and memory_resource_name() unwrap the returned objects, whether they come from create, list, or retrieve.

    Path 2: Archive a whole chat with ADK

    10 min

    Two parts of the agent deal with memory:

    travel_agent/agent.py
    from google.adk.tools.preload_memory_tool import PreloadMemoryTool

# Write: after every turn, send the whole session to the memory service
async def save_to_memory(callback_context):
    ctx = callback_context._invocation_context
    await ctx.memory_service.add_session_to_memory(ctx.session)

root_agent = LlmAgent(
    name="hotel_agent",
    model="gemini-2.5-flash",
    instruction="... Use what you remember about the guest ...",
    tools=[
        PreloadMemoryTool(),          # Read: search memory before the model answers
        generate_trip_image,
        airbnb_search_mcp_toolset,
    ],
    before_model_callback=before_model_modifier,
    after_agent_callback=save_to_memory,
)
    add_session_to_memory

    Sends every event in the session (guest messages, agent replies, uploaded images) to Memory Bank. Memory Bank extracts facts using the topics from step 3 and merges them with that user's existing memories.

    PreloadMemoryTool

    The model doesn't have to choose to call it. On every turn it searches memory with the guest's latest message and adds the results to the system instruction before the model answers.

    When to save

    • Every turn (what this repo does): memory stays current, but the whole session is sent again each time.
    • At the end of a session: call add_session_to_memory once from the code that closes the session. Cheaper, but a guest who opens a new chat before the old one closes won't see those memories yet.
    Not on Memory Bank yet, so no topics

    A plain adk web uses InMemoryMemoryService. It copies the raw events into RAM with no extraction, so your memory topics aren't used. Search only matches shared keywords, and everything is wiped when the process stops. The next step switches it to Memory Bank.

    Connect ADK to Memory Bank

    5 min

    The agent code doesn't change, because it already calls ctx.memory_service. You only change which memory service ADK creates.

    With adk web

    set -a; source .env; set +a      # put GOOGLE_CLOUD_PROJECT / LOCATION in the environment
adk web --memory_service_uri="agentengine://${AGENT_ENGINE_ID}"

    ADK creates a VertexAiMemoryBankService using the project and location from GOOGLE_CLOUD_PROJECT and GOOGLE_CLOUD_LOCATION.

    Where the topics come from

    ADK doesn't send memory topics. Memory Bank uses the topics saved on the bank that AGENT_ENGINE_ID points to. Point it at the bank you created in step 3. A bank created without topics falls back to the managed default topics.

    With your own Runner

    run_local.py (example)
    from google.adk.memory import VertexAiMemoryBankService
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService

from travel_agent import root_agent

memory_service = VertexAiMemoryBankService(
    project="your-project-id",
    location="us-central1",
    agent_engine_id="987654321",
)
runner = Runner(
    agent=root_agent,
    app_name="travel_agent",          # must match the scope the CLI uses
    session_service=InMemorySessionService(),
    memory_service=memory_service,
)
    Why the scopes line up

    ADK sends {"app_name": ..., "user_id": ...} as the scope. In adk web the app name is the folder name travel_agent and the user ID is user, the same defaults as python -m memory_bank add --user-id user. Facts written in step 4 show up for the agent right away.

    Test across sessions

    5 min

    Test path 1

    1. Write a fact with the CLI from step 4, if you haven't already.
    2. Start adk web with --memory_service_uri and pick travel_agent.
    3. Start a new session and type “Find me a place to stay in Chiang Mai for 3 nights.”
    4. The agent should ask about, or filter for, pet-friendly stays, because it sees the memory about Oreo.

    Test path 2

    1. In session A, type “I'd like a quiet, non-smoking room on a high floor.”
    2. Wait a moment. Memory generation runs in the background.
    3. Check with the CLI:
    python -m memory_bank list --user-id user
    1. Guest is traveling with a dog named Oreo.
2. Guest prefers a non-smoking room on a quiet high floor.
    1. In a new session B, type “Plan a trip to Bangkok for me.” The agent should use both the room preference and the dog.

    Test the memory topics

    1. In a new session, type “I'd like a non-smoking room, and I love really spicy food.”
    2. Wait a moment, then run python -m memory_bank list --user-id user.
    3. You should see the non-smoking room but nothing about spicy food. That means the custom topics are filtering what gets stored.
    No memories showing up?

    Check three things: adk web was started with --memory_service_uri, the User ID in the Web UI is user, and the app_name you wrote with is travel_agent.
